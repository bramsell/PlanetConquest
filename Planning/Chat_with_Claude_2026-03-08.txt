## The Core Problem: Dual Authority Over Vehicles

The fundamental issue is that vehicles have **two masters** giving them orders simultaneously, and neither knows what the other is doing:

**Master 1: The priority layers** (every 3 seconds) — These set `CurrentTarget`, `TargetResource`, `bHasTarget`, `TargetLocation`, `bAIAutonomousMode`, and call `SetTargetLocation()`. The recommitment logic in each layer's STEP 0 checks if vehicles are idle and re-sends them to targets.

**Master 2: The vehicle's own Tick** — The vehicle has its own behavioral logic running every frame. It follows `TargetLocation`, fires at `CurrentTarget`, captures `TargetResource`, manages `PostMineResource` transitions, and does autonomous target-finding when `bAIAutonomousMode` is true.

The problem is that `SetTargetLocation()` **clears** `CurrentTarget` internally (you even have comments noting this). So the recommitment logic in the priority layers does this:

```
Vehicle->SetTargetLocation(Mine->GetActorLocation());  // Clears CurrentTarget!
Vehicle->CurrentTarget = Mine;  // Set it back AFTER
```

This creates a one-frame window where `CurrentTarget` is null. If the vehicle's Tick runs during that frame, it may decide the mine attack is cancelled and switch to autonomous behavior, pick a new resource, or just stop. Then next decision cycle, the priority layer sees the vehicle is "idle" and recommits it — creating a stutter loop where the vehicle repeatedly starts attacking the mine, gets interrupted by its own Tick clearing state, and gets recommitted.

## Specific Bug Paths I Can See

**Mine attack stops before destroying:** The vehicle fires at the mine, the mine's health decreases, but between decision cycles one of these happens: (a) the vehicle's Tick autonomous logic finds a closer neutral resource and switches to capturing it, (b) `SetTargetLocation` in recommitment clears `CurrentTarget` and the vehicle stops firing for a frame, losing its lock, or (c) the vehicle enters capture range of the resource underneath the mine and starts trying to capture instead of continuing to fire.

**Mine destroyed but resource not captured:** `PostMineResource` is supposed to handle the transition — destroy mine, then capture the resource underneath. But `SetTargetLocation()` likely clears `PostMineResource` too (or clears `TargetResource`), so when the mine dies and the vehicle checks "what next?", the reference to the resource is gone.

**Priority layer conflicts:** All 6 layers run every cycle. A vehicle on P3 expansion duty attacking a mine could get pulled by P2 territory (which also wants to capture resources). Or P5 war prep could pull a vehicle that's mid-mine-attack, the mine lives, and the resource stays enemy-owned.

## The Flag Duplication Problem

You have both:
- The vehicle in a `PriorityXVehicles` array (checked by controller)
- `bInPX` flags on the vehicle itself (checked by vehicle Tick and other layers)

These can desync. A vehicle gets removed from `Priority3Vehicles` but `bInP3` stays true (or vice versa). Then one system thinks the vehicle is free while the other thinks it's busy.

## What I'd Recommend: A Unified Vehicle Task System

Instead of the current split-authority approach, give each vehicle a single, self-contained **task** that it owns and executes independently until completion or cancellation. The priority layers become task **assigners**, not task **executors**.

The concept would be something like:

```
USTRUCT()
struct FVehicleTask
{
    EVehicleTaskType Type;     // Capture, AttackMine, AttackBuilding, Defend, MoveTo, Aid
    int32 Priority;            // 1-6, so higher priority can preempt
    AActor* PrimaryTarget;     // The main thing we're going after
    AActor* SecondaryTarget;   // e.g., resource to capture AFTER mine destroyed
    FVector Destination;       // For MoveTo tasks
    bool bAutonomousContinue;  // After completing, find next similar task nearby?
    float SearchRadius;        // For autonomous continuation
    EOwnerTeam HostileTeam;    // Who to shoot at
};
```

The vehicle's Tick would then be a simple state machine driven entirely by its current task: move toward target, fire when in range, on target destroyed check for secondary target, on task complete either find next autonomous task or go idle. No external system would touch `TargetLocation` or `CurrentTarget` directly — only by assigning a new task.

The priority layers would become: assess what needs doing, find idle vehicles (task == None), assign tasks. A higher priority layer can **preempt** a lower priority task by replacing it, but only through the same task-assignment interface.

This eliminates the dual-authority problem because there's exactly one piece of state driving the vehicle, and exactly one way to change it.

## The Real Problem: Task State Is Scattered Across 10+ Fields

Moving from 6 arrays to a `CurrentPriority` enum on the vehicle is a good step, but it doesn't fix the core bug. The real issue is that a vehicle's "what am I doing" is spread across:

`CurrentTarget`, `TargetResource`, `PostMineResource`, `PrimaryTarget`, `TargetLocation`, `bHasTarget`, `bAIAutonomousMode`, `bPlayerAutonomousMode`, `bClusterOnlyMode`, `ActiveClusterID`, `ForcedHostileTeams`, `bHasAssignment`, `bInP1`–`bInP6`

That's ~16 fields that all have to be in a consistent state simultaneously, and `SetTargetLocation` wipes half of them. Every caller has to know the exact order to set things — call `SetTargetLocation` first, then re-set `CurrentTarget`, then re-set `PostMineResource`, don't forget `bAIAutonomousMode`... miss one and you get a silent bug.

## What I'd Build: FVehicleTask Struct

Bundle all of that into one struct that gets assigned atomically:

```cpp
UENUM(BlueprintType)
enum class EVehicleTaskType : uint8
{
    None,           // Idle — no task
    MoveTo,         // Move to location, no combat
    CaptureResource,// Move to resource, stand on it until captured
    DestroyMine,    // Attack mine, then capture PostMineResource
    AttackTarget,   // Attack a specific actor (vehicle, building, capital)
    Defend,         // Move to defensive position, engage hostiles in radius
    Aid             // Move to ally city, engage attackers
};

USTRUCT()
struct FVehicleTask
{
    GENERATED_BODY()

    EVehicleTaskType Type = EVehicleTaskType::None;
    int32 Priority = 0;                    // 1-6, matches your layer system
    
    // What to interact with
    TWeakObjectPtr<AActor> Target;         // Mine, building, vehicle, etc.
    TWeakObjectPtr<AResourceActor> Resource; // Resource to capture (or capture after mine dies)
    FVector Destination = FVector::ZeroVector;
    
    // Autonomous continuation
    bool bAutonomousContinue = false;      // Find next task in area when done?
    float SearchRadius = 5000.0f;
    int32 ClusterID = -1;                  // Cluster constraint for autonomous
    
    // Combat context
    TSet<EOwnerTeam> HostileTeams;
    
    // Who assigned this
    TWeakObjectPtr<AAITeamController> AssigningController;
};
```

Then on the vehicle, replace all 16 fields with:

```cpp
FVehicleTask CurrentTask;

void AssignTask(const FVehicleTask& NewTask);  // Atomic assignment
void ClearTask();                               // Go idle
bool IsIdle() const { return CurrentTask.Type == EVehicleTaskType::None; }
bool CanPreempt(int32 NewPriority) const { return NewPriority < CurrentTask.Priority; }
```

`AssignTask` sets everything at once — no ordering bugs, no half-initialized state. The vehicle's Tick reads from `CurrentTask` exclusively and never has to wonder which combination of flags is active.

CLAUDE:

You're working through the right design tension. Let me lay out the two approaches cleanly so you can see the tradeoffs.

## Option A: Merge P2 and P3 into "Income Layer"

One layer, one goal: maximize income. The layer looks at all resources it wants and figures out the full action chain per resource — if neutral, capture it; if enemy-owned, destroy mine then capture. The vehicle gets one compound task and executes it start to finish.

**Pros:** No ping-ponging between layers. The vehicle destroying a mine already "knows" it should capture the resource afterward. No race condition where P2 sees an unclaimed resource and steals the vehicle mid-mission. Simpler to reason about.

**Cons:** The layer becomes more complex internally. You lose the natural prioritization where nearby unclaimed resources get grabbed before committing to expensive mine attacks. An expansionist AI might send a vehicle across the map to attack a mine when there are uncaptured neutral resources right next to its city.

## Option B: Keep P2 and P3 Separate, But Make Them Aware of Each Other

P3 destroys a mine and sets `PostMineResource`. When P2 runs and sees a newly unclaimed resource, it checks: "Is any vehicle already on a P3 task with this resource as its PostMineResource?" If yes, skip it — that vehicle already has the claim. The resource effectively has a "reserved by" tag.

**Pros:** Keeps the natural priority ordering (cheap captures before expensive attacks). Each layer stays focused on one thing. The emergent P3→P2→P3 cycle you described still works, it just doesn't fight itself anymore.

**Cons:** Requires cross-layer awareness, which adds coupling. You need a reservation system so P2 knows what P3 has claimed.

## My Recommendation: Option A with Internal Prioritization

Merge them, but keep the priority ordering *inside* the merged layer. Something like this conceptually:

```
ExecuteIncomeLayer():
    // Build a single sorted list of "income opportunities"
    // Each opportunity is either:
    //   - Neutral resource (action: capture)        cost: low
    //   - Enemy resource (action: destroy mine + capture)  cost: high
    
    // Sort by: distance first, then prefer neutral over enemy at similar distance
    
    // For each opportunity, assign vehicle with compound task:
    //   If neutral: CaptureResource task
    //   If enemy-mined: DestroyMineThenCapture task (vehicle handles full chain)
```

This gives you the best of both worlds. Neutral resources still get grabbed first because they sort higher (cheaper, closer). But when a vehicle is sent to destroy a mine, it doesn't get confused by the resource becoming unclaimed mid-attack — it owns the entire operation.

The key insight is that your current P2/P3 split is really just an optimization heuristic (do cheap things first), not a fundamentally different goal. Both layers want the same thing: more income. The split created an implicit handoff between layers that's hard to coordinate correctly.

## What This Means for the Task System

A `DestroyMineThenCapture` task type would handle the full chain internally in the vehicle's Tick:

```
case DestroyMineThenCapture:
    if mine target is valid and alive:
        move toward mine, fire when in range
    else if mine destroyed and resource is neutral:
        switch to capturing the resource (same task, next phase)
    else if resource got claimed by someone else:
        find next opportunity or go idle
```

No layer switch. No `PostMineResource` handoff. No race condition. The vehicle just executes its mission.

The AI controller doesn't need to recommit the vehicle or track the mine-to-resource transition at all. It assigned the task, the vehicle handles it. The controller only cares again when the vehicle reports back as idle.
