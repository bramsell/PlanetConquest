The logs tell the whole story. Look at this line:

```
Camera after attach: World P=-20.00 Y=161.83 R=-0.00 | Relative P=-40.00 Y=-0.00 R:-180.00
```

You set `Camera->SetRelativeRotation(FRotator(220, 180, 0))` but Unreal normalized it to `P:-40 Y:0 R:-180`. That's mathematically equivalent in Euler angles, but the R:-180 roll means the camera is upside down, which flips the effective pitch direction. So instead of looking 40° below the arm's forward direction (down at the city), it's looking 40° above it (up and away from the city).

Then look at the ARM_DIAG:

```
ArmRoot Rot=P:-60.0 Y:161.8 R:180.0
```

The arm itself has R:180 roll. This is the spring arm's internal behavior — when the pitch goes below a certain threshold, Unreal's rotation decomposition can flip the roll to 180°. Your planet mode works despite this because the camera's relative rotation of (220, 180, 0) happens to produce the correct world rotation through a double-negation of flips. But when you explicitly set these values after reattachment, the normalization breaks the cancellation.

This is exactly why I suggested the "let Unreal tell you" approach. Replace your manual target calculation in `EnterCityEditorMode` with the temporary-configure-and-read-back method. Here's the key change — replace everything from `// Define target city-editor parameters` through the `TargetLocation = CityCenter` line:

```cpp
// Capture camera's CURRENT world transform (start point) BEFORE any changes
TransitionStartWorldPos = Camera->GetComponentLocation();
TransitionStartWorldRot = Camera->GetComponentRotation();

// Save current spring arm state
FVector OldPawnLocation = GetActorLocation();
FRotator OldPawnRotation = GetActorRotation();
float OldArmLength = CameraArm->TargetArmLength;
FRotator OldCameraRelative = Camera->GetRelativeRotation();
bool OldLag = CameraArm->bEnableCameraLag;

// Temporarily configure spring arm in city-editor final state
// Use current viewing yaw so camera stays on same side of city
float CurrentViewingYaw = Camera->GetComponentRotation().Yaw;
float CityArmYaw = CurrentViewingYaw - 180.0f; // Arm opposite to view direction

CameraArm->bEnableCameraLag = false;
SetActorLocation(CityCenter);
SetActorRotation(FRotator(-60.0f, CityArmYaw, 0.0f));
CameraArm->TargetArmLength = CityEditorStartDistance;
Camera->SetRelativeRotation(FRotator(CurrentCameraTilt, CurrentCameraRotation, CurrentCameraRoll));

// Force spring arm to evaluate immediately
CameraArm->TickComponent(0.0f, ELevelTick::LEVELTICK_All, nullptr);

// Read back the ACTUAL resulting camera world transform
TransitionEndWorldPos = Camera->GetComponentLocation();
TransitionEndWorldRot = Camera->GetComponentRotation();

// Store parameters for reattachment (exactly what we just configured)
TargetYaw = CityArmYaw;
TargetPitch = -60.0f;
TargetOrbitDistance = CityEditorStartDistance;
TargetCameraTilt = CurrentCameraTilt;
TargetCameraRotation = CurrentCameraRotation;
TargetLocation = CityCenter;

// Restore original state
SetActorLocation(OldPawnLocation);
SetActorRotation(OldPawnRotation);
CameraArm->TargetArmLength = OldArmLength;
Camera->SetRelativeRotation(OldCameraRelative);
CameraArm->bEnableCameraLag = OldLag;
CameraArm->TickComponent(0.0f, ELevelTick::LEVELTICK_All, nullptr);

// NOW detach for free-flight interpolation
Camera->DetachFromComponent(FDetachmentTransformRules::KeepWorldTransform);
```

This works because the transition end position and rotation are read directly from the spring arm's own output. When the transition completes and you reattach with the same parameters, the spring arm produces the identical world transform — no normalization mismatch, no roll flip, no guessing about axis conventions.

Do the same for `ExitCityEditorMode` — temporarily reattach, configure for planet mode, tick the arm, read the result, restore, detach.
